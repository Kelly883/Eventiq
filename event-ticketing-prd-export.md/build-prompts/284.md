Let's make sure the calendar feature is properly secured and doesn't expose sensitive data.

All three endpoints (GET /api/events/public/calendar, GET /api/events/public/calendar/day/:date, GET /api/events/public/calendar/range) are public and don't require authentication, but they need protection against abuse and data leaks:

1. Rate limiting — Enforce 30 requests per minute per IP address on all three endpoints. This prevents scraping and denial-of-service attacks. Use a rate-limiting middleware (like express-rate-limit or Laravel's built-in throttle) to implement this.

2. Data filtering — Always filter to published events only on the server side. Never trust the client to filter — a malicious user could modify the request to see unpublished or draft events. Check status='published' in the database query before returning any event.

3. Sensitive data — Don't expose organizer data beyond what's needed for display: name, avatar, branding colors are fine. Don't expose email addresses, phone numbers, payment info, or internal IDs. Filter the organizer object in the API response to only include public fields.

4. Query validation — Validate all query parameters on the server:
   - month/week format must be valid ISO format (YYYY-MM or YYYY-Www)
   - date format must be valid ISO8601 (YYYY-MM-DD)
   - price range must be valid numbers (min <= max, both >= 0)
   - location must be a string (no SQL injection)
   - category must match an existing category ID
   Reject invalid requests with 400 Bad Request.

5. Pagination — If the calendar returns a large number of events, implement cursor-based pagination to prevent memory exhaustion. Don't allow unlimited result sets.

6. CORS — If the frontend is on a different domain, configure CORS to allow requests from your frontend domain only. Don't use wildcard '*' for public endpoints — be specific.

7. HTTPS only — Ensure all API calls use HTTPS. Don't allow HTTP fallback.
