We need three state managers so the event pages don't handle data fetching themselves and can share state cleanly.

1. Event List state — Tracks the list of events, loading states (initial load vs. loading more), the selected tab (Upcoming, Past, Drafts), search query, pagination cursor, and any errors. Should support: loading the first page of events for a given status, loading more pages (append, don't replace), changing the tab (clears list and reloads with new status filter), and searching (filters on client side). Use swr to fetch from GET /api/organizer/events with ?status and ?page query parameters. Cache the results so switching tabs doesn't refetch unnecessarily.

2. Event Detail state — Tracks a single event, its ticket tiers, loading state, and errors. Loads an event by ID from GET /api/organizer/events/:eventId. This is used by EventEditPage to pre-fill the form. Cache this so if the user navigates away and back, the data is still available.

3. Event Form state — Tracks the form's dirty state (has the user made changes?), validation errors, and submission state (idle, saving, success, error). This is local to the EventCreatePage and EventEditPage components but should be managed separately from the form values themselves (which react-hook-form handles). When the user clicks 'Save as Draft' or 'Publish Event', this state tracks whether the request is in flight and shows the spinner.

Keep business logic out of the pages — pages should just call methods and react to state changes. Use swr's built-in error handling and revalidation. For the form state, you can use React Context or a simple useState hook since it's local to the page.
