Let's make sure the dashboard and ticket endpoints are properly secured and users can only access their own data.

**Authentication** — All five endpoints (GET /api/my-tickets, GET /api/users/me/dashboard-overview, GET /api/users/me/dashboard-preferences, PATCH /api/users/me/dashboard-preferences, GET /api/tickets/:ticketId/details) must check that the user is authenticated via bearer token in the Authorization header. Reject with 401 if the token is missing, invalid, or expired.

**Authorization** — Use Laravel Policies to enforce that users can only access their own data:
- GET /api/my-tickets: Query only tickets where userId == authenticated user's ID. Never return other users' tickets, even if they guess a ticket ID.
- GET /api/users/me/dashboard-overview: Only return metrics for the authenticated user.
- GET /api/users/me/dashboard-preferences: Only return preferences for the authenticated user.
- PATCH /api/users/me/dashboard-preferences: Only allow updating the authenticated user's preferences.
- GET /api/tickets/:ticketId/details: Check that the ticket belongs to the authenticated user. If not, return 403 (not 404 — don't reveal that the ticket exists).

**Data Filtering** — On the backend:
- GET /api/my-tickets: Always filter by userId on the server side. Don't trust the client to send the right userId.
- Delivery status and delivery history should only be visible to the ticket owner.
- QR codes should only be visible to the ticket owner.
- Organizer contact info and payment details should be masked or hidden.

**Rate Limiting** — Enforce rate limits to prevent abuse:
- GET /api/my-tickets: 20 requests/min per user
- GET /api/users/me/dashboard-overview: 20 requests/min per user
- GET /api/users/me/dashboard-preferences: 20 requests/min per user
- PATCH /api/users/me/dashboard-preferences: 10 requests/min per user (lower because it's a write)
- GET /api/tickets/:ticketId/details: 20 requests/min per user

**Input Validation** — Validate all inputs on the backend:
- GET /api/my-tickets: filter must be one of 'all', 'upcoming', 'past'. dateRange must be one of '7days', '30days', '90days', 'all'. page and limit must be positive integers. search must be a string (max 100 chars).
- PATCH /api/users/me/dashboard-preferences: defaultTicketFilter must be one of 'all', 'upcoming', 'past'. defaultDateRange must be one of '7days', '30days', '90days', 'all'. Boolean fields must be true/false.
- GET /api/tickets/:ticketId/details: ticketId must be a valid UUID format.

**Token Handling** — On the frontend:
- Store the auth token securely (HttpOnly cookie or secure storage, not localStorage if possible).
- Include the token in the Authorization header for all requests to these endpoints.
- If a request returns 401, redirect to login and clear the stored token.
- Implement token refresh if using JWT with expiration.

**Sensitive Data** — Never expose:
- Other users' ticket IDs or QR codes
- Payment information or order totals for other users
- Delivery addresses or contact info for other users
- Organizer private info or contact details
