Let's lock down the checkout and payment system so only authorized users can purchase and view their orders.

Authentication — All five endpoints (POST /api/cart/verify, POST /api/checkout/create-payment-intent, POST /api/webhooks/payment-provider, GET /api/orders/:orderId, GET /api/my-tickets) must verify the user is authenticated. The webhook endpoint is an exception — it should verify the webhook signature from the payment provider (Stripe) instead of requiring a user token, since it's called by Stripe's servers, not the client.

Authorization — POST /api/cart/verify and POST /api/checkout/create-payment-intent should verify that the user owns the items in their cart (cross-check against the events and ticket tiers). GET /api/orders/:orderId should use the orders schema's Policy: only the user who created the order can read it (user_id == AUTH_USER_ID). GET /api/my-tickets should only return tickets owned by the authenticated user (user_id == AUTH_USER_ID).

Payment Intent Security — POST /api/checkout/create-payment-intent should create a pending order record before requesting the payment intent from Stripe. Store the payment_intent_id in the orders table. This prevents users from creating multiple payment intents for the same cart. The client secret returned to the frontend should only be used once — if the user abandons checkout and comes back, create a new payment intent.

Webhook Signature Verification — POST /api/webhooks/payment-provider must verify the webhook signature using Stripe's verification method (stripe.Webhook.constructEvent). Never trust webhook data without verifying the signature — this is how you prevent fraudulent webhook calls. Log all webhook attempts (successful and failed) for audit purposes.

Inventory Atomicity — When POST /api/webhooks/payment-provider processes a successful payment, it must transactionally: update the order status to 'completed', create ticket records, and decrement inventory. Use database transactions to ensure no race conditions — two simultaneous purchases can't both succeed if there's only one ticket left.

PCI Compliance — Never handle raw card data on your server. All card information must be collected by Stripe's CardElement on the frontend and processed by Stripe's API. Store only the payment_intent_id and gateway_response (which contains tokenized data, not raw card numbers).

Rate Limiting — Apply rate limits to prevent abuse: POST /api/cart/verify (30/min), POST /api/checkout/create-payment-intent (5/min per user — prevent spam payment intents), POST /api/webhooks/payment-provider (no limit, but log all attempts), GET /api/orders/:orderId (60/min), GET /api/my-tickets (30/min).

Data Validation — POST /api/cart/verify should validate that quantities are positive integers and that ticket tier IDs exist. POST /api/checkout/create-payment-intent should validate the total amount matches the cart (recalculate server-side, don't trust the client). POST /api/webhooks/payment-provider should validate that the order exists and the amount matches before marking it as completed.
