We need to make sure things fail gracefully when something goes wrong.

PushNotificationSettingsSection (on DeliverySettingsPage):
- Network failure when loading preferences on page mount → show a banner at the top of the section with 'Failed to load preferences' and a 'Retry' button. Don't show the toggles yet.
- Network failure when toggling a preference → revert the toggle to its previous state, show an inline error message below the toggle that failed, and include a 'Retry' button. The user can retry without reloading the page.
- Permission denied when requesting browser notification permission → show a message explaining 'Notifications are blocked in your browser settings. You can enable them in your browser preferences.' Don't save the preference as enabled.
- 401 (session expired) → redirect to the login page.
- 403 (user doesn't have permission to update their own preferences — shouldn't happen, but handle it) → show an error banner 'You don't have permission to change these settings.'
- 422 (validation error from the backend) → show the specific validation error message from the server.

AdminPushTemplateManagementPage:
- Network failure when loading templates on page mount → show a full-screen error with 'Failed to load templates' and a 'Retry' button. Don't show the list or editor.
- Network failure when saving a template → show an error banner at the top of the page with 'Failed to save template' and a 'Retry' button. Keep the form filled in so the user doesn't lose their work.
- Network failure when deleting a template → show a confirmation dialog 'Are you sure?' and if they confirm, attempt the delete. If it fails, show an error message 'Failed to delete template' with a 'Retry' button.
- 401 (session expired) → redirect to the login page.
- 403 (user is not an admin) → redirect to /admin or show an 'Access Denied' page.
- 404 (template doesn't exist) → if the user is editing a template and it gets deleted by another admin, show an error 'This template was deleted' and clear the editor.
- 422 (validation error) → show the specific validation error message from the server (e.g., 'Title must be at most 65 characters').
- 500 (server error) → show an error banner with 'Something went wrong' and a 'Retry' button.

Send Test Push Modal:
- Network failure when sending the test → show an error message in the modal 'Failed to send test notification' with a 'Retry' button.
- 404 (user doesn't exist) → show 'User not found. Check the User ID and try again.'
- 422 (validation error) → show the specific error from the server.
- Success → show a success message 'Test notification sent!' and close the modal after 2 seconds.

Device token registration (on app startup):
- Network failure when registering the device token → log the error to the console but don't block the app. The user can still use the app, they just won't receive push notifications until the token is registered. Optionally, retry in the background after a delay.
- 401 (user not authenticated) → this is expected on app startup before login. Don't show an error.
- 500 (server error) → log the error and retry in the background.

Device token deletion (on logout):
- Network failure when deleting the device token → log the error but don't block the logout. The user is still logged out. Optionally, retry in the background.

General error handling:
- All error messages should be user-friendly, not technical jargon. Instead of 'ECONNREFUSED', say 'Check your internet connection.'
- Don't show raw error codes or stack traces to the user.
- For 5xx errors, suggest 'Try again in a few moments' or 'Contact support if this persists.'
- Always provide a way to retry failed operations without reloading the page.
