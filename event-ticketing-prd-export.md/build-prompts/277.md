We need to lock down the developer portal and API key system so only authorized users can access and manage their own integrations.

Authentication and authorization:
- All endpoints (/api/developer/api-keys, /api/developer/webhooks, /api/developer/api-logs, /v1/events, /graphql) must check that the user is authenticated. Reject with 401 if not.
- The DeveloperPortalPage should check that the user has the 'organizer' role. Show 'Access Denied' if not.
- All Laravel Policies must be enforced: users can only read, update, and delete their own keys and webhooks. The policy checks that [user_id] == [AUTH_USER_ID].

API key security:
- Raw API keys are generated, hashed with bcrypt, and only the hash is stored in the database. The raw key is returned in the response ONCE and is never retrievable again.
- The key prefix is stored so users can identify which key they're using, but the full key is never shown after creation.
- When a key is revoked, set the revoked_at timestamp (soft delete) — don't permanently delete the record. This preserves audit history.
- API key authentication for the /v1/events and /graphql endpoints must use a dedicated middleware that extracts the key from the Authorization header, looks it up in the database, checks that it's not revoked, and verifies the requested scope.
- Rate limiting should be applied to API key endpoints to prevent brute force attacks.

Webhook security:
- A secret is generated for each webhook and stored in the database. This secret is used to sign webhook payloads with HMAC-SHA256.
- When delivering a webhook, include the signature in the X-Webhook-Signature header. Receiving systems should verify this signature to ensure the payload came from us.
- Webhook URLs must be validated (HTTPS required, no localhost, no private IP ranges).
- Track webhook delivery attempts in webhook_delivery_logs with status, response code, and response body for debugging.
- If a webhook fails repeatedly (e.g., 5 consecutive failures), mark it as inactive and notify the organizer.

Audit logging:
- All API key and webhook operations (create, update, delete, revoke) must create an auditLog entry with the action, user ID, resource ID, and timestamp.
- All API calls made with an API key must be logged in auditLogs with the action 'api_call', the key ID, the endpoint, method, status, and IP address.
- These logs are used to populate the API Logs tab and provide an audit trail.

Scope enforcement:
- API keys have scopes (e.g., 'events:read', 'orders:read'). The API key middleware must check that the requested endpoint is allowed by the key's scopes.
- For GraphQL, scopes are checked at the resolver level — each query/mutation checks that the API key has the required scope.

Data exposure:
- Never return the full API key or webhook secret in API responses. Only return the prefix for keys and never return the secret for webhooks.
- The newly-created key is shown once in the frontend modal, but this is client-side only — the backend never returns it again.
