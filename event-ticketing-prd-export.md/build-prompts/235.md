We need three state managers so the pages don't handle data fetching themselves.

1. Delivery Preferences state — Tracks the user's delivery_preferences (push_notifications_enabled, push_order_confirmation, push_event_reminder, push_checkin_alert, push_promotional_offers), loading state, and any errors. Should support: loading preferences on page mount, updating a single preference field, and handling the async PATCH request to /api/users/me/delivery-preferences/update. When a preference updates, optimistically update the local state immediately, then make the API call. If the call fails, revert the state and surface the error.

2. Push Templates state (admin only) — Tracks the list of all push templates, the currently selected template for editing, loading states (initial load, saving, deleting), and errors. Should support: loading all templates from GET /api/admin/push-templates, selecting a template to edit, creating a new template (POST /api/admin/push-templates), updating an existing template (PATCH /api/admin/push-templates/:templateId), deleting a template (DELETE /api/admin/push-templates/:templateId), and clearing the selection to start a new template. Handle pagination if there are many templates.

3. Test Push Notification state (admin only) — Tracks whether a test notification is being sent, the result (success/error), and any error message. Should support: sending a test push via POST /api/admin/push-templates/send-test with a user_id and template content, and clearing the result after the user dismisses it.

Keep all business logic out of the components — components should just call methods on the state managers and react to state changes. Use React Context or a state management library (like Zustand or Redux) to make these available throughout the app.
