Let's make sure the compliance feature is properly secured and only admins can access sensitive audit data.

All five endpoints (GET /api/admin/compliance/audit-logs/list, GET /api/admin/compliance/audit-logs/:logId/details, GET /api/admin/compliance/audit-logs/export, POST /api/admin/compliance/audit-logs/bulk-tag, POST /api/admin/compliance/reports/generate) should check that the user is logged in and has the 'Admin' role — reject with 401 if not authenticated, 403 if not admin.

Specific security concerns:

1. Data masking — IP addresses should be masked in API responses (show only first 2 octets, e.g., '192.168.***.*'). Request/response bodies should be sanitized to remove sensitive fields like passwords, card numbers, API keys. User agents should be truncated if they're very long. Only admins should see this data, and it should never be logged to client-side analytics.

2. Rate limiting — Enforce strict rate limits to prevent abuse: 20 requests/min for list and detail endpoints, 5 exports/min, 10 bulk operations/min, 5 report generations/min. This prevents admins from hammering the API or exporting massive amounts of data.

3. Export security — All exports should be logged to the auditLogs table with action='data_export_requested' and classification='sox_financial'. This creates an audit trail of who exported what and when. Exports should be streamed directly to the client (not stored on disk) to avoid leaving sensitive data on the server.

4. Audit log immutability — The auditLogs table should be append-only. Admins can tag logs and mark them as reviewed, but they cannot edit or delete individual log entries. This prevents tampering with the audit trail.

5. Sensitive field encryption — If the auditLogs table stores sensitive data (like credit card numbers in payment audit trails), encrypt these fields at rest. Decrypt only when needed and only for admins.

6. CSRF protection — All POST endpoints should validate CSRF tokens to prevent cross-site request forgery.

7. Frontend auth check — On the frontend, check that the user is an admin before rendering the compliance pages. This is a UX check, not a security boundary — the backend must always verify admin status.

8. Session validation — On every compliance page load, validate that the user's session is still active and they still have admin role. If not, redirect to login or not authorized page.
