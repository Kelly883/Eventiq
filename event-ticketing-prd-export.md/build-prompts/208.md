We're building a push notification system with two pages. Let me walk you through what each one does and how to build it.

First, PushNotificationSettingsSection — this is NOT a standalone page. It's a new section that integrates into the existing DeliverySettingsPage at /settings/delivery-preferences. Don't create a new route. Instead, add a new card titled 'Push Notifications' to that existing page, positioned below the 'Email Notifications' section. Inside the card, build a master toggle labeled 'Enable Push Notifications' that controls whether all push notifications are on or off. Below that, add four individual toggles in separate rows: 'Ticket Confirmations', 'Event Reminders', 'Check-in Alerts', and 'Promotional Messages'. When the master toggle is OFF, all four sub-toggles should be disabled (grayed out). When any toggle changes, immediately call PATCH /api/users/me/delivery-preferences/update with the updated delivery_preferences fields (push_notifications_enabled, push_order_confirmation, push_event_reminder, push_checkin_alert, push_promotional_offers). Show a loading spinner on the toggle while the request is in flight. If it succeeds, keep the toggle in its new state. If it fails, revert the toggle and show an inline error message with a retry button. On first load, fetch the current delivery preferences and populate all toggles. When the user first enables push notifications, request browser notification permission using the Notification API — if they grant it, proceed with saving. If they deny it, show a message explaining they won't receive notifications.

Second, AdminPushTemplateManagementPage at /admin/settings/push-templates — this is a full admin page for managing push notification templates. Use a two-column layout: the left column is a list of all push templates (fetched from GET /api/admin/push-templates), the right column is the template editor. Each template in the list shows its name and type. Clicking a template loads it into the editor on the right. The editor form has fields for: template name (text input), type (dropdown or text), title (text input with a character counter showing current/65), and body (textarea with a character counter showing current/178). Below the form, show a sidebar listing available placeholder variables like {{user.name}}, {{event.title}}, {{ticket.number}} — these are just for reference so admins know what they can use. At the bottom of the editor, add a 'Save' button and a 'Delete' button (delete only appears when editing an existing template). Also add a 'Send Test Notification' button that opens a modal. In the modal, ask for a User ID and a button to send. When clicked, POST to /api/admin/push-templates/send-test with the user_id and the current template content. Show a success message when the test is sent. At the top of the page, add a 'Create Template' button that clears the editor and lets the admin create a new template. When creating, POST to /api/admin/push-templates. When updating, PATCH to /api/admin/push-templates/:templateId. When deleting, DELETE to /api/admin/push-templates/:templateId. Handle loading states: show skeleton loaders in the template list and disable the editor form while loading. Handle empty state: if no templates exist, show an illustration with 'No push templates created yet' and a 'Create Template' button. Handle saving state: show a spinner on the Save button and disable the form. Handle errors: show an error banner at the top with a retry button for 500 errors, redirect to login for 401, and show 'Access Denied' for 403.
