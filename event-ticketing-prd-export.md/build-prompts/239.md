We need three state managers so the compliance pages don't handle data fetching themselves.

1. Audit Logs state — Tracks the list of audit events, loading states (initial load vs. loading more), current filters (date range, action type, actor role, target type, status, classification), search query, sort options (field and order), pagination (page, limit), and any errors. Should support: loading the first page of logs, loading more (append to existing list), changing filters (reset to page 1 and reload), searching (debounce 300ms), sorting, and polling for new events every 30 seconds. The polling should append new events to the top without replacing existing ones. Store the selected log ID separately so the detail modal can fetch full details. Handle pagination cursors internally.

2. Audit Log Details state — Tracks a single expanded log's full details (request/response data, before/after values, geolocation, etc.), loading state, and errors. Loads from GET /api/admin/compliance/audit-logs/:logId/details when a row is expanded.

3. Compliance Reports state — Tracks: list of previously generated reports, loading state, current report being previewed (with summary stats and data), report generation progress (jobId, status, estimated time), scheduled reports, compliance checklist status, and any errors. Should support: generating a new report (POST /api/admin/compliance/reports/generate with async polling), fetching the list of past reports (GET /api/admin/compliance/reports/list), scheduling automatic generation (POST /api/admin/compliance/reports/schedule), and fetching compliance checklist (GET /api/admin/compliance/checklist). When a report is generated, poll the job status until it completes, then fetch the report details.

Keep business logic out of the pages — pages should just call methods and react to state changes. Use React Context or a state management library (Zustand, Redux, etc.) to make this state available app-wide.
