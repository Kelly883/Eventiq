We're building a role and permission management system for event organizers. This step creates two pages: one for admins to manage all users' roles, and one for regular users to see their own permissions.

AdminRoleManagementPage at /admin/roles — This is a power-user dashboard for admins only. Build a dense, scannable table layout with these columns: user email, user name, current role (with color-coded badges: Admin=red, Organizer=blue, Attendee=green, Support=orange), permission count, and actions. Above the table, add a filter bar with: search field (searches email/name), role dropdown filter, and permission status filter. Add a checkbox in the header to select all visible users, and checkboxes on each row for bulk selection.

When users are selected, show a bulk action bar below the table with: a role dropdown to assign a new role, a reason text field (optional), and an 'Apply' button. Clicking 'Apply' opens a confirmation modal showing how many users will be affected and what's changing. On confirm, it calls POST /api/admin/roles/assign and shows a success toast with the count.

Each row should be expandable (click the row or an expand icon) to show a detailed permission breakdown — a grid of permission names with toggle switches for grant/revoke. Toggling a permission opens a confirmation modal (especially for high-risk permissions) and calls POST /api/admin/permissions/update.

At the bottom, add a collapsible 'Audit Log' section that loads from GET /api/admin/audit-log/list. Show the 10 most recent changes in a compact timeline: admin name, action (role_assigned, permission_granted, etc.), target user, timestamp, and reason if provided. Make it sortable by date.

Loading state: show 5 skeleton rows in the table with placeholder shimmer. Empty state: show 'No users found' with a button to reset filters. Error states: 401 redirects to login with 'Session expired' toast, 403 shows 'Access Denied — only admins can manage roles' with a back button, 500 shows an error banner with a retry button.

UserPermissionsPage at /settings/permissions — This is a read-only page for users to see their own role and permissions. Build a vertical card layout. At the top, show a large role badge with the role name, a description of what that role allows, and a count of granted permissions. Below that, create collapsible cards for each permission category (Event Management, Ticket Management, Analytics, User Management). Each card lists the specific permissions granted in that category with checkmarks. If a permission is not granted, show it grayed out.

For each permission category, add an inline 'Request Access' button. Clicking it opens a modal with a text field for an optional reason and a 'Submit Request' button. This calls POST /api/users/me/request-permission. After submission, show a success toast.

Below the permission categories, add a 'Pending Requests' section showing all permission requests from GET /api/users/me/permission-requests. Each request shows: permission name, status badge (yellow=pending, green=approved, red=denied), request date, and if approved/denied, the admin's reason. If the user is an admin, add a link 'Manage other users' permissions' that routes to /admin/roles.

Loading state: show skeleton cards for role summary and permission categories. Empty state (no permissions): show 'You have no permissions yet' with an explanation and a 'Request Access' button. Error states: 401 redirects to login, 500 shows an error banner with retry.

Both pages should be mobile-friendly — stack vertically, no horizontal scroll. Use React Router for navigation and TanStack Query for data fetching.
