## 2. Security Assessment

### 2.1 Authentication — STRONG ✅
- All endpoints check `$request->user()` and return 401 if null
- Bearer token auth via `BearerTokenAuth` middleware
- `ResetAuthState` middleware clears guard cache per-request (prevents cross-request leakage)

### 2.2 Authorization (IDOR Prevention) — STRONG ✅
- `Gate::forUser($user)->authorize()` used consistently
- `EventPolicy::view()` enforces strict ownership: `(int) $event->organizer_id === (int) $organizer->id`
- No fallback via `event->user_id` (prevents stale-user_id bypass)
- Users cannot read, update, delete, or upload banners to other users' events (403 verified)

### 2.3 Mass Assignment — STRONG ✅
- `mapEventData()` explicitly whitelists fields — user cannot inject `organizer_id`, `user_id`, `flag_reason`, etc.
- `mapTierData()` explicitly whitelists tier fields
- `unset($payload['id'])` prevents tier ID injection on create
- `banner_image_url` is commented out from direct payload mapping (prevents external URL injection)

### 2.4 File Upload Security — STRONG ✅
- Validation: `required|file|image|mimes:jpeg,jpg,png,gif,webp|max:5120`
- Double size check: validator `max:5120` (5MB) + explicit `getSize() > 5*1024*1024` byte check
- Content verification: `getimagesize()` validates actual image content (prevents extension spoofing)
- Only allows JPEG, PNG, GIF, WebP (no SVG, no PDF-as-image)
- Returns 413 for oversized (correct HTTP semantics)
- ClamAV hook exists for production virus scanning

### 2.5 Input Validation — STRONG ✅
- `StoreEventRequest` / `UpdateEventRequest` FormRequest classes
- `prepareForValidation()` normalizes camelCase → snake_case (frontend compat without sacrificing validation)
- `end_datetime` must be `after_or_equal:start_datetime`
- `capacity` must be `min:0` integer
- `status` restricted to `draft|published` via `in:` rule
- Max 10 ticket tiers per event

### 2.6 SQL Injection — NONE FOUND ✅
- No `whereRaw`, `DB::raw`, or `orderByRaw` in EventController
- All queries use Eloquent parameter binding

### 2.7 Rate Limiting — PRESENT ✅
- `throttle:organizer-events` (60/min) on list/show/update/delete
- `throttle:organizer-events-create` (30/min) on create
- `throttle:organizer-banner` (10/min) on banner upload

### 2.8 Idempotency — PRESENT ✅
- `Idempotency-Key` header support on create
- 24h cache window prevents duplicate event creation

## 3. Security Gaps & Recommendations

### 3.1 MEDIUM: Error Information Leakage
**Finding:** `store()` catch block returns `$e->getMessage()` to the client (line 140).  
**Risk:** Database errors, file paths, or internal details could leak.  
**Recommendation:** Log the full error server-side, return generic "Failed to create event" to client. Only expose `$e->getMessage()` when `APP_DEBUG=false` is false (and even then, sanitize).

### 3.2 MEDIUM: Missing Authorization on `viewAny`
**Finding:** `EventPolicy::viewAny()` only checks if user has organizer role, not resource ownership.  
**Risk:** Low — the controller additionally filters by `organizer_id` in the query, so users only see their own events. But the policy itself is broader than the implementation.  
**Recommendation:** This is fine as-is because the controller enforces ownership. Document that `viewAny` is intentionally permissive because the query filters by organizer.

### 3.3 LOW: No CSRF Protection on State-Changing Routes
**Finding:** API routes use bearer tokens (stateless), so CSRF is not applicable.  
**Recommendation:** Ensure these routes are NOT in the `web` middleware group (they're not — confirmed in `api.php`).

### 3.4 LOW: Banner Upload Path Traversal
**Finding:** The banner filename is generated by Laravel's Storage (safe), but `extractStoragePath()` parses URLs.  
**Risk:** Low — only used on already-stored URLs for deletion.  
**Recommendation:** Ensure stored paths are never user-controlled filenames.

### 3.5 INFO: ClamAV Not Enabled in Tests
**Finding:** `config('services.clamav.enabled', false)` defaults to false.  
**Recommendation:** Document that production must enable ClamAV or alternative virus scanning.

## 4. Performance Analysis

### 4.1 N+1 Query Prevention — GOOD ✅
- `index()` uses `with(['ticketTiers', 'organizer'])` eager loading
- `without('analyticsEventsMetric')` removes default eager load not needed for lists
- Selective column loading on ticketTiers reduces memory

### 4.2 Pagination — GOOD ✅
- Default 15 per page, capped at 100
- `paginate()` with `orderByDesc('created_at')`

### 4.3 MEDIUM: Slug Generation Race Condition
**Finding:** The slug uniqueness check (`while (Event::where('slug', $slug)->exists())`) is inside the transaction but uses a query-per-iteration loop.  
**Risk:** With high concurrency on identical titles, could loop many times. The unique index on `slug` provides a final guard (would throw on duplicate).  
**Recommendation:** Add a unique DB index on `slug` (should already exist based on migration). Consider appending a short random suffix instead of sequential counter.

### 4.4 LOW: Job Dispatch in Request Lifecycle
**Finding:** `IncrementTotalEventsCreated::dispatch()` is called after the transaction commits.  
**Risk:** If job dispatch fails, the event is created but the counter isn't incremented (logged as warning).  
**Recommendation:** This is acceptable — the counter is derived data and can be recalculated.

### 4.5 INFO: Missing Database Index
**Recommendation:** Ensure composite index on `(organizer_id, status, created_at)` for the list query filter + sort.

## 5. Edge Cases

| Edge Case | Handling | Status |
|---|---|---|
| Concurrent create with same title | Slug unique index + loop | ✅ Handled |
| Transaction rollback on tier failure | `DB::transaction` wraps all | ✅ Handled |
| File upload with spoofed extension | `getimagesize()` content check | ✅ Handled |
| Delete already-deleted event | `find()` returns null → 404 | ✅ Handled |
| Update with non-existent tier ID | `exists:ticket_tiers,id` validation | ✅ Handled |
| Zero capacity | `min:0` allows it | ✅ Handled |
| Empty ticket_tiers array | `nullable` + `array` | ✅ Handled |
| Banner upload without file | `required` validation | ✅ Handled |
| Very large page size | Capped at 100 | ✅ Handled |
| Negative page number | Laravel normalizes | ✅ Handled |

## 6. What I'd Fix Before Real Users

### MUST FIX (before production)
1. **Error message leakage** — Don't return `$e->getMessage()` to clients in production
2. **Add DB unique index on `slug`** — Guard against race condition on slug generation

### SHOULD FIX (soon)
3. **Add composite DB index** on `(organizer_id, status, created_at)` for list performance
4. **Enable ClamAV** or virus scanning in production for banner uploads
5. **Add rate limit headers** to response for client awareness

### NICE TO HAVE
6. **Event status workflow** — Currently `draft↔published` with no state machine. Add validation that prevents publishing events without ticket tiers.
7. **Banner image resizing** — Store multiple sizes (thumbnail, medium, full) for performance
8. **Event versioning/audit log** — Track who changed what and when

---

## 7. Summary

The organizer event endpoints are **well-secured** and **functionally correct**. The implementation demonstrates:

- ✅ Consistent authorization via Policy + Gate
- ✅ Strong input validation with FormRequest normalization
- ✅ Mass-assignment protection via explicit field mapping
- ✅ Secure file upload with content verification
- ✅ Proper soft deletes
- ✅ Rate limiting and idempotency support
- ✅ Transaction safety for multi-step operations

The two items I would address before real users start creating events are the error message leakage and the slug race condition guard. Everything else is solid for a production launch.
