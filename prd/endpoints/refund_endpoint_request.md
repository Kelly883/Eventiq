# Refund Endpoint Request

POST /api/refunds/request

## Description

REQUEST: { ticketId (string, UUID, required), reason (string, required - 'event_cancelled'|'personal_circumstances'|'duplicate_purchase'|'other'), explanation (string, optional, max 500 chars), refundMethod (string, required - 'original_payment_method'|'store_credit'|'alternative_payment_method') }
PROCESS: 1. Verify auth token and extract userId 2. Query tickets by ticketId 3. Check user owns ticket via Policy 4. Query orders by orderId to get purchase details 5. Query refund_policies by eventId 6. Validate refund eligibility: check if within refundWindowDays, check if event has started (if afterEventStart, check allowRefundsAfterEventStart), check if reason is in allowedRefundMethods 7. Calculate refund amount based on policy (originalAmount * refundPercentage) 8. Check if refund method is allowed by policy 9. Create refund_requests record with status='pending' or 'approved' based on requiresApproval flag 10. If auto-approve (requiresApproval=false or amount < autoApproveThreshold), set status='approved' and queue refund processing job 11. Create auditLog entry: action='refund_requested', ticketId, userId, refundAmount 12. Send notification to user with refund reference number and expected timeline
SUCCESS (200): { refundRequestId (string), status (string), refundAmount (decimal), expectedProcessingDays (integer), referenceNumber (string), message (string) }
ERRORS: 400 (invalid input, invalid reason, invalid refund method), 401 (unauthenticated - attempt token refresh → if fails, redirect to login), 403 (user doesn't own ticket, refund window closed, event policy doesn't allow refunds), 404 (ticket or event not found), 409 (duplicate refund request for same ticket), 429 (rate limited), 500 (database error)
SECURITY: Auth required (bearer token). Ticket ownership enforced via Policy. Refund window validation server-side. Rate limit 5 requests/hour per user to prevent abuse. All requests logged to auditLogs.
