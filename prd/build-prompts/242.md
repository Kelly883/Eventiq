We need state managers so the DeveloperPortalPage tabs don't handle data fetching themselves. Use Zustand to create three stores:

1. API Keys store — Tracks the list of API keys, loading state, and errors. Should support: fetching keys from GET /api/developer/api-keys, creating a new key via POST /api/developer/api-keys (which returns the full key once), revoking a key via DELETE /api/developer/api-keys/:keyId, and clearing the newly-created key from display after the user closes the modal. The store should expose: keys array, isLoading boolean, error string or null, newlyCreatedKey (the full key shown once), and methods: fetchKeys(), createKey(name, scopes), revokeKey(keyId), clearNewKey().

2. Webhooks store — Tracks webhook configurations, loading state, and errors. Should support: fetching webhooks from GET /api/developer/webhooks, creating a webhook via POST /api/developer/webhooks, deleting a webhook via DELETE /api/developer/webhooks/:webhookId, and sending a test payload. The store should expose: webhooks array, isLoading boolean, error string or null, and methods: fetchWebhooks(), createWebhook(url, events), deleteWebhook(webhookId), sendTestPayload(webhookId).

3. API Logs store — Tracks recent API call logs, loading state, and errors. Should support: fetching logs from GET /api/developer/api-logs with pagination. The store should expose: logs array, isLoading boolean, error string or null, hasMore boolean, and methods: fetchLogs(cursor?), loadMore().

All stores should handle errors gracefully and expose error messages for display in the UI. Keep business logic out of the components — components should just call store methods and react to state changes.
