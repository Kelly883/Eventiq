We need three state managers so the pages don't handle data fetching and caching themselves.

**Dashboard Overview State** — Manages the summary metrics, next upcoming event, and recent activity feed for UserDashboardPage. Should fetch from GET /api/users/me/dashboard-overview. Tracks loading state (initial load vs. refreshing), error state, and the aggregated data (totalTickets, upcomingEventsCount, pastEventsCount, totalSpent, nextUpcomingEvent, recentActivity). Should support: initial load, manual refresh, and auto-refresh every 30 seconds (if autoRefreshEnabled is true in preferences). When auto-refreshing, don't show a loading spinner — just update the data in the background.

**Tickets List State** — Manages the paginated list of tickets for UserTicketsDashboardPage. Fetches from GET /api/my-tickets with query params for filter (all/upcoming/past), dateRange (7days/30days/90days/all), search query, and pagination (page, limit=20). Tracks: loading state (initial load vs. loading more), error state, the ticket list, current filters, search query, pagination cursor, and whether there are more pages. Should support: loading the first page, loading more pages (append, don't replace), changing filter (reset to page 1), changing date range (reset to page 1), searching (reset to page 1), and manual refresh. Handle pagination internally — the page just calls 'load more' and the state appends to the existing list.

**Ticket Detail State** — Manages a single ticket for TicketDetailPage. Fetches from GET /api/tickets/:ticketId/details. Tracks: loading state, error state, and the full ticket details (id, eventId, eventTitle, eventDate, eventVenue, organizer, tier, status, purchaseDate, orderId, QR code, delivery status, delivery history, related tickets). Should support: loading by ticketId and manual refresh.

**Dashboard Preferences State** — Manages user preferences for UserDashboardPage. Fetches from GET /api/users/me/dashboard-preferences. Tracks: loading state, error state, and preferences (defaultTicketFilter, defaultDateRange, showRecommendations, showActivityFeed, autoRefreshEnabled). Should support: loading preferences and updating them via PATCH /api/users/me/dashboard-preferences. When preferences change, the dashboard should re-apply them (e.g., if autoRefreshEnabled is toggled off, stop the 30-second refresh).

Use TanStack Query (React Query) for all data fetching, caching, and background updates. Set appropriate stale times: dashboard overview 30 seconds, tickets list 1 minute, ticket detail 2 minutes, preferences 5 minutes. Keep business logic out of the pages — pages should just call hooks and react to state changes.
