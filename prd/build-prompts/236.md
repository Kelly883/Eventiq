We need three state managers so the refund pages don't handle data fetching themselves. These should use React hooks and manage the complete refund lifecycle.

Refund Request State — Manages the form and submission for UserRefundRequestPage. Tracks: the ticket details (event name, date, tier, price), the refund policy for that event (window days, percentage, allowed methods, processing time), form field values (reason, explanation, refundMethod), validation errors, loading state, and submission result (refundRequestId, status, refundAmount, referenceNumber, expectedProcessingDays). Should support: loading ticket details by ticketId from the URL, loading the refund policy by eventId, validating form fields (reason required, explanation max 500 chars, refundMethod required and must be in policy.allowedRefundMethods), calculating refund amount in real-time (originalAmount × refundPercentage), submitting the form to POST /api/refunds/request, and handling errors (401, 403, 404, 409, 429, 500). Keep business logic out of the page — the page just calls methods and reacts to state changes.

Refund Status State — Manages the display of a submitted refund request for UserRefundStatusPage. Tracks: the refund request details (ticket info, amounts, reason, submission date), current status (pending/approved/rejected/processing/completed), status timeline with all stage changes and timestamps, rejection reason if applicable, expected completion date if approved, refund method, and appeal history (count, last appeal date). Should support: loading refund request details by refundRequestId from the URL, polling for status updates (check every 10 seconds for new status changes), submitting an appeal (POST to /api/refunds/:refundRequestId/appeal), and handling errors (401, 403, 404, 500). The timeline should be computed from the status history — don't store it separately.

Admin Refund Dashboard State — Manages the dashboard for AdminRefundDashboardPage. Tracks: list of all refund requests, loading state, summary metrics (pending count, total amount pending, approval rate, average processing time), active filters (event, status, date range, amount range, reason), search query, sort column and direction, pagination cursor, and selected rows for bulk actions. Should support: loading the initial list from GET /api/admin/refunds/list, filtering by any combination of event/status/date/amount/reason, searching by ticket ID/email/event name, sorting by any column, paginating with cursor-based pagination, selecting/deselecting rows for bulk actions, approving/rejecting selected requests (POST to /api/admin/refunds/approve and /api/admin/refunds/reject), exporting as CSV, and polling for real-time updates every 30 seconds. Handle errors (401, 403, 500). The metrics should be recalculated whenever the list changes.

All three state managers should use React hooks (useState, useEffect, useCallback) and keep the logic testable. Don't mix UI concerns with data fetching — separate them cleanly.
