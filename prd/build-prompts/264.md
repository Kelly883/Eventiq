Now we need to connect the refund pages to the rest of the app and ensure proper authentication and authorization.

Routing — Add three routes to the app router:
- /my-tickets/:ticketId/refund-request → UserRefundRequestPage (authenticated users only)
- /my-tickets/:ticketId/refund-status → UserRefundStatusPage (authenticated users only)
- /admin/refunds/dashboard → AdminRefundDashboardPage (admin users only)

Authentication guards — For the first two routes, check that the user is logged in. If not, redirect to /login with a return URL so they come back after signing in. For the admin dashboard, check that the user has the 'Admin' role. If not, show a 403 error page.

Navigation wiring — From the ticket detail page (or wherever users see their tickets), add a 'Request Refund' button/link that goes to /my-tickets/:ticketId/refund-request. From the refund request confirmation screen, the 'View Status' button navigates to /my-tickets/:ticketId/refund-status. From the refund status page, add a back button that goes back to the ticket detail page. From the admin dashboard, clicking on a refund request row should expand it inline (no page navigation). For admins, add a link in the admin menu to /admin/refunds/dashboard.

Deep linking — Support deep links to /my-tickets/:ticketId/refund-request and /my-tickets/:ticketId/refund-status. If the user isn't logged in, redirect to /login first, then to the refund page after signing in. If the user doesn't own the ticket, show a 403 error.

Notifications — When a refund request is submitted successfully, show a success toast with the reference number. When a refund status changes (approved/rejected/processing/completed), send a notification to the user (in-app toast or email, depending on your notification system). When an appeal is submitted, show a confirmation toast.

Breadcrumbs — On UserRefundRequestPage and UserRefundStatusPage, show breadcrumbs: Home > My Tickets > [Event Name] > Refund Request/Status. This helps users understand where they are.
