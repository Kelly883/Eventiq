We need to ensure the QR code verification and check-in system is properly secured against unauthorized access, data leaks, and abuse.

Authentication & Authorization:
- All six endpoints (POST /api/tickets/generate-qr, POST /api/tickets/verify-qr, POST /api/tickets/:ticketId/check-in, POST /api/tickets/:ticketId/void, GET /api/venue/check-in/sync, GET /api/organizer/events/:eventId/check-in-analytics) require a valid bearer token. Reject with 401 if missing or invalid.
- POST /api/tickets/generate-qr requires the user to own the ticket (enforced via Policy: [user_id] == [AUTH_USER_ID]). Reject with 403 if not.
- POST /api/tickets/verify-qr and POST /api/tickets/:ticketId/check-in require 'VenueStaff' or 'Organizer' role. Reject with 403 if the user lacks this role.
- POST /api/tickets/:ticketId/void requires 'Organizer' or 'Admin' role. Reject with 403 if not.
- GET /api/venue/check-in/sync requires 'VenueStaff' or 'Organizer' role and event authorization (user is organizer or assigned venue staff for that event).
- GET /api/organizer/events/:eventId/check-in-analytics requires the user to own the event. Reject with 403 if not.

Encryption & Data Protection:
- QR code payloads are encrypted with AES-256 on the server side. The encryption key is stored in environment variables and never exposed to the client.
- QR code secrets are hashed with bcrypt (cost 12) before storage. Never store plaintext secrets.
- Decryption happens server-side only — encrypted payloads are never sent to the client in plaintext. The client receives only the encrypted qrCodeData string.
- All sensitive data in API responses (email addresses, personal details) should be minimized. Return only what's necessary for venue staff to verify the ticket.

Rate Limiting:
- POST /api/tickets/generate-qr: 10 generations/min per user (prevent abuse of QR generation)
- POST /api/tickets/verify-qr: 60 verifications/min per user (high limit for venue scanning)
- POST /api/tickets/:ticketId/check-in: 60 check-ins/min per user (high limit for venue scanning)
- POST /api/tickets/:ticketId/void: 10 voids/min per user (prevent bulk voiding)
- GET /api/venue/check-in/sync: 30 syncs/min per user (prevent excessive polling)
- GET /api/organizer/events/:eventId/check-in-analytics: 20/min per user (prevent excessive queries)

Audit Logging:
- All QR generations are logged to auditLogs with: action='qr_generated', ticketId, userId, timestamp.
- All verification attempts are logged with: action='qr_verified', ticketId, userId, result (valid/invalid/expired/fraud_flagged), timestamp.
- All check-ins are logged with: action='ticket_checked_in', ticketId, userId (staff member), timestamp. Make this idempotent — checking in the same ticket twice logs only once.
- All voids are logged with: action='ticket_voided', ticketId, userId, reason, timestamp.

Fraud Detection:
- Track qrCodeScannedCount and lastQrScanAt. If the same QR code is scanned multiple times in rapid succession (e.g., 3+ times in 10 seconds), flag it as potential fraud and log to fraud_events.
- If a ticket is scanned from geographically impossible locations (e.g., two venues 1000km apart within 5 minutes), flag as fraud.
- If a ticket is checked in after the event end date + grace period, reject the check-in.
- If a ticket is fraud-flagged with status='auto_blocked', reject check-in and show 'This ticket is blocked'.

Data Validation:
- Validate all input: ticketId (UUID format), qrCodeData (base64 string), venueId (UUID if provided), reason (max 500 chars), dates (ISO8601 format).
- Reject malformed requests with 400 and clear error messages.
- Sanitize all user inputs before logging or displaying.

Offline Mode Security:
- Cached check-ins stored in localStorage should be encrypted or at least obfuscated (not plaintext).
- When syncing cached check-ins, verify each one again server-side — don't trust the client's cached data.
- Implement a sync timeout: if sync takes longer than 5 minutes, show a warning and allow manual retry.

Token Management:
- Implement token refresh: if a token is about to expire, refresh it automatically before making the next API call.
- If token refresh fails, redirect to login.
- Store tokens securely (httpOnly cookies if possible, or secure localStorage with encryption).
