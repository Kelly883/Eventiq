We need state managers so the three organizer profile pages don't handle data fetching themselves. Create three separate state managers:

1. Organizer Public Profile state — Tracks a single organizer's public profile data (avatar, name, bio, contact info, social links, branding colors, stats). Loads from GET /api/organizers/:organizerId. Handles loading state, error state, and the organizer data. Should support: loading a profile by ID, refetching when the ID changes, and clearing data when unmounting. This is used by OrganizerPublicProfilePage.

2. Organizer Events state — Tracks the list of events for a specific organizer. Loads from GET /api/organizers/:organizerId/events. Supports filtering by status (upcoming/past) and pagination (limit/offset). Handles loading, error, and event list data. Should support: loading events for an organizer ID, changing filters (status, date range, category), loading more events (append, don't replace), and clearing data. This is also used by OrganizerPublicProfilePage.

3. Organizer Me state — Tracks the current user's own organizer profile (if they are an organizer). Loads from GET /api/organizers/me. Includes all profile data (including private fields like email, phone, notification preferences). Handles loading, error, and profile data. Should support: loading the current user's profile on app startup, updating the profile after edits, uploading avatar, updating settings, and clearing data on logout. This is used by OrganizerProfileEditPage and OrganizerProfileSettingsPage.

For each state manager, keep business logic out of the pages — pages should just call methods like loadProfile(), updateProfile(), uploadAvatar(), and react to state changes. Use React hooks (useState, useEffect) to manage the state. Consider using a context provider or a state management library like Zustand or Redux if the app already uses one. Handle debouncing for search/filter changes so API calls don't fire on every keystroke.
