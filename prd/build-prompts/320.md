We need to make sure errors don't break the admin experience and provide clear guidance on what went wrong.

**Authentication Errors (401)** — If any API call returns 401 (invalid/expired token), attempt to refresh the token (if your auth system supports it). If refresh succeeds, retry the original request. If refresh fails or is not supported, redirect to the login page with a toast: 'Session expired. Please log in again.' Store the current page URL so we can redirect back after login.

**Authorization Errors (403)** — If any API call returns 403 (user not admin), show a full-page error: 'Access Denied — only admins can view this page' with a back button. This shouldn't happen if the frontend guard is working, but handle it gracefully anyway.

**Validation Errors (400)** — If a request fails validation (e.g., invalid filter params, missing required fields), show a toast with the error message from the backend. For form submissions (suspend reason, refund reason), show inline field errors below the input.

**Server Errors (500)** — If a request returns 500 (database error, server crash), show an error banner at the top of the page: 'Something went wrong. Please try again.' Include a 'Retry' button that re-runs the failed query. Log the error to a monitoring service (e.g., Sentry) for debugging.

**Network Errors** — If the request fails due to network issues (no internet, timeout), show a toast: 'Network error. Check your connection and try again.' Include a 'Retry' button.

**Dashboard-Specific Errors**:
- If GET /api/admin/dashboard/overview fails, show a skeleton state with an error banner and retry button. Don't show stale data
