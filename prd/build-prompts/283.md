Let's lock down the dashboard so only authorized organizers can access their own data.

All six endpoints (GET /api/organizer/dashboard/overview, GET /api/organizer/dashboard/events, GET /api/organizer/dashboard/events/:eventId, GET /api/organizer/dashboard/activity-feed, GET /api/organizer/dashboard/preferences, PATCH /api/organizer/dashboard/preferences) must verify the auth token and extract the organizerId. Reject with 401 if the token is missing, invalid, or expired.

Enforce the 'Organizer' role on all endpoints. If a user doesn't have this role, return 403 with 'User does not have Organizer role'.

Implement ownership checks: the overview, events, and activity-feed endpoints should only return data for events owned by the authenticated organizer. Use the Policy system to enforce this — a user can only read their own events' metrics and activity.

For the preferences endpoints (GET and PATCH), ensure that a user can only read and update their own preferences. Use the Policy to enforce that [user_id] == [AUTH_USER_ID].

Implement rate limiting on all endpoints: 20 requests per minute per user for read operations (GET), 10 requests per minute per user for write operations (PATCH). This prevents abuse and DoS attacks.

Validate all query parameters on the backend:
- dateRange must be one of: 7days, 30days, 90days, all
- eventFilter must be one of: all, upcoming, past, draft
- limit must be a positive integer (max 100)
- offset must be a non-negative integer
- sortBy must be one of: date, revenue, tickets
- Reject with 400 if validation fails

For the PATCH /api/organizer/dashboard/preferences endpoint, validate that the request body only contains allowed fields (defaultEventFilter, defaultDateRange, expandedEventId, showActivityFeed, autoRefreshEnabled). Reject any other fields with 400.

On the frontend, check the user's role before rendering the dashboard. If the user doesn't have the 'Organizer' role, show 'Access Denied' and a back button instead of loading the dashboard.

Store the auth token securely (httpOnly cookie or secure localStorage). Never expose the token in API responses or logs.

When the token expires (401 response), redirect to the login page and clear the stored token. Show a 'Session expired' toast so the user knows why they were logged out.
