We need state managers to handle role and permission data across both pages without fetching repeatedly.

Create three state managers using Zustand:

1. Admin Role Management Store — Tracks: the list of users (from GET /api/admin/users/list), selected user IDs for bulk actions, current filters (role, search query, permission status), sort order, loading state, and any errors. Should support: loading the user list with filters, selecting/deselecting users, clearing selection, changing filters (which resets pagination), and updating a user's role after a successful change. When a role is assigned, update the affected users in the list without refetching everything.

2. Admin Audit Log Store — Tracks: the audit log entries (from GET /api/admin/audit-log/list), filters (targetUserId, action type), pagination state, and loading state. Should support: loading the audit log with filters, sorting by date, and pagination. Keep this separate so the audit log can load independently of the user list.

3. User Permissions Store — Tracks: the current user's role, their permissions (from GET /api/users/me/permissions), pending permission requests (from GET /api/users/me/permission-requests), and loading state. Should support: loading the user's permissions, adding a new pending request to the list after submission, and updating a request's status if the user is an admin and approves/denies their own request (unlikely but handle it).

For AdminRoleManagementPage, use TanStack Query to fetch the user list and audit log (Query handles caching and refetching). Use the Zustand store to manage UI state (selected users, filters, bulk action state). When a bulk role change succeeds, invalidate the user list query so it refetches.

For UserPermissionsPage, use TanStack Query to fetch permissions and requests. Use Zustand to track which permission category is expanded (optional, for UX).

Keep business logic out of components — stores should handle all state transitions. Components should call store methods and react to state changes.
