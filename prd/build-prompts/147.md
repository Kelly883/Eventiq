We need five API endpoints to handle the entire checkout and payment flow. All endpoints require authentication except where noted.

1. POST /api/cart/verify — Verifies that items in the user's cart are still available and prices haven't changed. Takes a JSON body with an array of cart items (ticket_tier_id and quantity). Queries the ticket_inventory and pricing_windows tables to check current availability and prices. Returns { valid: boolean, items: [...], errors: [...] }. If any item is no longer available or the price has changed, include it in the errors array. This prevents users from purchasing with stale data.

2. POST /api/checkout/create-payment-intent — Creates a payment intent with the payment provider (Stripe or PayPal). First, create a pending Order record in the database with status='pending'. Then create OrderItem records for each item in the cart. Call the payment provider's API to create a payment intent with the total amount. Store the payment_intent_id in the Order. Return { clientSecret: string, orderId: string } to the frontend. The clientSecret is used to initialize the payment UI on the frontend.

3. POST /api/webhooks/payment-provider — Handles incoming webhooks from the payment provider (Stripe or PayPal). This is the critical endpoint for order fulfillment. Verify the webhook signature using the provider's SDK (this prevents spoofed webhooks). For a successful payment event (e.g., charge.succeeded from Stripe), transactionally: update the Order status to 'completed', create Ticket records for each OrderItem (generate unique QR codes), decrement the ticket_inventory, log the payment to the payments table, update analytics tables (analytics_events_metrics, analytics_sales_timeline), and queue a job to email the tickets to the user. Return 200 OK to acknowledge receipt. For failed payments, update the Order status to 'failed'.

4. GET /api/orders/:orderId — Retrieves the details of a specific order for the authenticated user. Query the Order by ID, then load its related OrderItems and join with TicketTier and Event data. Return the full order with all line items and event details. Check that the order belongs to the authenticated user (use Laravel policies). Return 404 if not found, 403 if the user doesn't own the order.

5. GET /api/my-tickets — Retrieves all tickets purchased by the authenticated user, grouped by event. Query the tickets table filtered by user_id, eager-load Event and TicketTier relationships. Group the results by event_id. Return an array of events, each with its tickets. Include the QR code data for each ticket so the frontend can render it.

All endpoints should validate input, check authentication, and return appropriate HTTP status codes (200 for success, 400 for bad input, 401 for auth failure, 403 for permission denied, 404 for not found, 500 for server errors).
