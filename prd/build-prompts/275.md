Let's make sure the fraud detection system is properly secured so only authorized admins can access it and fraud decisions are tamper-proof.

**Admin-Only Access** — Both FraudDetectionDashboardPage and FraudTransactionReviewModal should check that the user has the 'Admin' role before rendering. If a non-admin tries to access /admin/fraud/dashboard, redirect them to the home page with a 'Access Denied' toast. This check should happen in the router guard or in the page component itself. The backend endpoints GET /api/admin/fraud/flagged-transactions and GET /api/admin/fraud/transaction-details/:fraudEventId also check the 'Admin' role via Laravel Policy — the frontend should trust these checks and handle 403 responses gracefully.

**Authentication Required** — All fraud detection API calls require a valid bearer token in the Authorization header. The frontend should include the token automatically (via an axios interceptor or fetch wrapper). If a token is missing or expired, the backend returns 401 and the frontend should redirect to login.

**Rate Limiting** — The backend enforces rate limits: 20 requests/min for GET /api/admin/fraud/flagged-transactions and GET /api/admin/fraud/transaction-details/:fraudEventId, and 10 requests/min for POST /api/admin/fraud/review-transaction. The frontend should respect these limits and not spam the API. For example, don't refresh the transactions list more than once per 30 seconds, and don't allow the admin to submit multiple review decisions in quick succession.

**Fraud Detection SDK Security** — The fraud detection SDKs (Sift Science and Stripe Radar) are initialized on the backend only. The frontend never has access to API keys or sensitive SDK configuration. When the frontend calls POST /api/checkout/create-payment-intent, the backend runs fraud detection internally and returns only the risk score and verification flag — never the raw fraud factors or internal scoring details.

**Audit Trail** — Every fraud decision (approve/reject) is logged to the backend's auditLogs table with: the admin's user ID, the fraud event ID, the decision (approve/reject), optional notes, timestamp, and IP address. The frontend doesn't need to do anything special — the backend logs this automatically when POST /api/admin/fraud/review-transaction is called. Make sure the frontend doesn't expose the audit log to non-admins.

**Data Sensitivity** — The fraud dashboard shows sensitive data: customer emails, payment card fingerprints, IP addresses, device fingerprints. This data should only be visible to admins. Make sure the frontend doesn't cache this data in localStorage or send it to analytics. If the page is left open on a shared computer, the data is still visible — admins should be trained to lock their screens.

**Webhook Verification** — The backend webhook endpoint POST /api/webhooks/payment-provider verifies the webhook signature using the payment provider's SDK (Stripe, Paystack, etc.). The frontend doesn't handle webhooks directly, but make sure the backend is configured correctly with the webhook signing secret in environment variables.
