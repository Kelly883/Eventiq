We need to make sure the refund system is secure and users can only access their own data.

Authentication — All three endpoints (POST /api/refunds/request, GET /api/refunds/:refundRequestId/status, GET /api/admin/refunds/list, etc.) require a valid bearer token. Reject with 401 if the token is missing or invalid. Implement token refresh: if the token is expired, attempt to refresh it automatically. If refresh fails, redirect to login.

User authorization — For UserRefundRequestPage and UserRefundStatusPage, verify that the authenticated user owns the ticket (via the Policy: [user_id] == [AUTH_USER_ID]). If not, return 403 'Access Denied — you don't own this refund request'. This check must happen server-side — don't trust the client.

Admin authorization — For AdminRefundDashboardPage, verify that the user has the 'Admin' role. If not, return 403 'Access Denied — only admins can view refund dashboard'. This check must happen server-side.

Refund window validation — Server-side, validate that the refund request is within the refundWindowDays specified in the refund policy. Don't trust the client's calculation. If outside the window, return 403 'Refund window closed'.

Refund eligibility — Server-side, validate that the refund reason is in the policy's allowedRefundMethods, the refund method is in policy.allowedRefundMethods, and if the event has started, check policy.allowRefundsAfterEventStart. Return 403 if any check fails.

Duplicate prevention — Before creating a refund request, check if one already exists for this ticket. If so, return 409 'Duplicate refund request for same ticket'.

Rate limiting — Enforce rate limits: 5 requests/hour per user for POST /api/refunds/request (to prevent abuse), 20/min per user for read operations (GET endpoints). Return 429 if exceeded.

Audit logging — Log all refund actions to auditLogs: action='refund_requested', ticketId, userId, refundAmount, timestamp. Log all admin actions: action='refund_approved' or 'refund_rejected', refundRequestId, adminId, timestamp. This creates an audit trail.

Payment gateway security — Never expose the Stripe or PayPal API keys in client code or API responses. Store them only in server environment variables. When processing refunds, use the payment gateway's server-side API, not the client-side SDK.

Data validation — Validate all inputs server-side: reason must be one of the allowed values, explanation max 500 chars, refundMethod must be one of the allowed values. Reject with 400 if validation fails.
